# AI-Native Org Patterns

Framework derived from Anthropic's Claude Code team restructuring — shifting bottlenecks from code-writing to verification, review, and security.

**Use when:** Asked about AI workflow adoption, team process redesign, or measuring Claude Code impact at team scale.

**Do not use when:** The question is about code-level discipline (use `karpathy-guidelines`), PR review mechanics for a specific PR (use `code-review-excellence`), individual AI feature design (use `progressive-complexity-ladder`), or individual developer productivity without org scope.

**Related skills:** `karpathy-guidelines` (code-level discipline), `code-review-excellence` (review mechanics), `progressive-complexity-ladder` (AI feature design).

---

## Phase 1: Process Audit — Find the Noisiest Workflow

Start with the most expensive or most dreaded process, not the easiest one.

**Questions to identify candidates:**
- What process do engineers complain about most?
- What takes the most calendar time per week (meetings, rituals, reports)?
- What fails silently and causes rework downstream?

**For each candidate, ask:**
1. Does this process still serve its original purpose?
2. Can it be automated entirely (feedback summaries, status reports, routine reviews)?
3. Can it be eliminated without consequence?
4. Can it be compressed (weekly → async, sync → PR comment)?

**Anti-pattern:** Starting with "easy wins" that don't change the actual bottleneck.

## Phase 2: JIT Planning (Replace Design Docs with Prototypes)

**Old model:** 6-month roadmaps, design docs requiring sign-off before any code.  
**AI-native model:** Prototype first, get internal users, act on feedback, discuss in PRs.

**When to use JIT:**
- Feature scope is uncertain or dependent on user response
- Design doc would take longer to write than the prototype
- Team has fast internal dogfooding loop

**When to keep upfront design:**
- External API contracts (can't iterate in prod)
- Security/compliance boundaries (must be reviewed before code exists)
- Cross-team dependencies with long coordination lead time

**Execution pattern:**
```
1. Build minimal prototype (hours, not days)
2. Get it in front of real internal users
3. Capture feedback in the PR description
4. Iterate or pivot based on actual behavior
```

## Phase 3: AI/Human Review Tiering

Explicit split — define who (what) reviews what before the PR is opened.

| Review type | Owner | Rationale |
|---|---|---|
| Style, formatting, linting | AI | No judgment required; fully automatable |
| PR description quality | AI | Structural check; AI can verify completeness |
| Bug detection, test coverage gaps | AI | Pattern matching; AI excels here |
| Domain expertise (business logic, data model) | Human | Context not in code |
| Legal / compliance / privacy | Human | Liability; AI can assist but not decide |
| Security-sensitive code (auth, crypto, secrets) | Human | Stakes too high for AI sole ownership |
| Product taste (UX copy, feature feel) | Human | Subjective; requires user empathy |

**Implementation:**
- Document this split in your team's PR template or CLAUDE.md
- Block merge on human review only for the right-column categories
- Use AI review (Claude Code, GitHub Actions) as a pre-filter, not a gate replacement

## Phase 4: Ask Claude First for Context

Before pinging a code author or scheduling a sync:

1. Ask Claude: "What does this module do and why is it structured this way?"
2. Ask Claude: "What are the callers of this function and what edge cases do they handle?"
3. Ask Claude: "What changed in this area in the last 3 months and why?"

**This eliminates:** Interrupt-driven context requests, "quick questions" that break flow, waiting for async replies.

**Escalate to humans when:** Claude's answer contains speculation, the question involves intent/business context not in code, or the answer affects a decision with legal/security scope.

## Phase 5: Adoption Metrics

Track these three to measure whether AI-native patterns are taking hold:

| Metric | What it signals | Target |
|---|---|---|
| **Onboarding ramp time** | Time from hire to first PR merged | Week 1 (AI helps new engineers ship immediately) |
| **PR cycle time** | Open → merged, p50 and p90 | Declining trend; p90 spikes identify CI/build bottlenecks |
| **Claude-assisted commits** | % of commits with AI involvement | 100% adoption (not 100% AI-written) |

**Anti-metric:** Lines of code generated by AI — measures volume, not quality or adoption.

**Cadence:** Review monthly; look for trend direction, not absolute numbers.

---

## Three Org Principles (Non-Negotiable)

1. **Dogfood relentlessly** — if your team builds AI tools, everyone uses them daily, including managers
2. **Keep it flat** — managers start as ICs; avoid coordination layers that slow the prototype loop
3. **Kill obsolete processes explicitly** — give engineers permission to question and eliminate rituals; document what was killed and why so it doesn't resurrect

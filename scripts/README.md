# scripts/

Utility scripts used by the harness. Python scripts are stdlib-only except where a package is listed in `setup/harness-requirements.txt` — those import from the harness-owned venv at `<harness root>/.venv-tools`, never from a target repo's environment. A target repo's venv belongs to its owner and can be pruned or relocked at any time; anything the harness depends on there dies silently when that happens.

## Setup & Stack

| Script | Purpose |
|---|---|
| `generate-project-stack.sh` | Auto-detect project language, runtime, package manager, deps, test commands, Docker services → writes `PROJECT_STACK.md`. Called by `install.sh` and `update.sh` automatically. |
| `setup/check-settings-json.sh` | Strict-JSON validation for one or more settings files/templates (`check-settings-json.sh <file> [<file> ...]`). Exit 1 if any file is unparseable, naming the line and column. Claude Code parses `.claude/settings.json` as strict JSON — no comments, no content after the closing brace — and silently ignores a malformed file, so every permission rule and hook in it stops working. `install.sh` runs it on `templates/settings.json.template` before copying; `update.sh` runs it on the regenerated harness settings plus the per-project template; `/kiro:harness-validate` runs it as a blocking step. No-ops with a warning if `python3` is absent. |
| `setup/repair-settings-json.py` | Repairs a project's `.claude/settings.json` broken by a trailing `//` comment block (shipped by the pre-2026-08-12 template): peels the block into `.claude/settings.notes.md` and leaves valid JSON behind. Idempotent — valid files report `OK` and are untouched; anything not fixable by removing a trailing comment block is reported `MANUAL` rather than guessed at. `repair-settings-json.py <project_dir> [...]`, `--dry-run` to preview. Run on every `install.sh` and `update.sh`, and on **every session start** by `hooks/claude/session-start-hook.sh` (which locates it via `$HOME/.sdd-harness-root` and prints `[SETTINGS-REPAIRED]` only when it actually changed something) — so a settings file broken by an old install costs one session instead of lasting until someone runs `update.sh`. |
| `setup/check-harness-deps.sh` | **The dependency guard.** Verifies, heals, and declares every package the harness relies on, then reports each one as `ok` / `healed` / `FAILED` / `skipped`. Two manifests drive it: `setup/harness-requirements.txt` installs into the harness-owned `.venv-tools` (no target repo has these, so no target repo can prune them), and `setup/repo-requirements.txt` installs into each registered repo's venv **and** declares it in that repo's own manifest via `setup/declare-repo-deps.py`. Declaration is the half that makes it stick: `raindrop-setup.sh` and `headroom-setup.sh` used to `pip install <pkg> -q 2>/dev/null` into repo venvs and write nothing to the repo's manifest, so the package looked like an orphan and the repo's next `uv sync` / lockfile regen / dependency prune deleted it — while the swallowed output meant the harness printed "Done." either way. Run by `install.sh` and `update.sh` *before* `raindrop-setup.sh` (whose auto-instrument pass needs the SDK present). Also reports machine-level tooling that no repo can declare: whether the `headroom` binary is resolvable (including when its directory is off PATH), whether the proxy is listening, and whether `ANTHROPIC_BASE_URL` routing is wired — flagging the one dangerous combination, routing pointed at a proxy that refuses the connection. It distinguishes curl exit 7 (nothing listening → real failure) from 28 (listening but slow → fine), because collapsing the two reports a false outage on a healthy machine. `SDD_DEP_CHECK_ONLY=1` reports drift without changing anything; `SDD_SKIP_DEP_DECLARE=1` installs but never touches repo manifests. Exit 1 if anything could not be healed. |
| `setup/harness-requirements.txt` | Packages the harness itself imports → installed into `.venv-tools`. Format: `<pip-spec> [import-name]`. Add a line here rather than importing from whatever `python3` a target repo happens to provide. |
| `setup/repo-requirements.txt` | Packages that must import inside a **target repo's** interpreter (currently `raindrop-ai`, which instruments the repo's own source). Installed *and* declared in that repo. Everything the harness merely calls for itself belongs in `harness-requirements.txt` instead. |
| `setup/declare-repo-deps.py` | Idempotently declares packages in a target repo's manifest: `pyproject.toml` → `[dependency-groups] harness = [...]` (PEP 735), else `requirements.txt` → `requirements-harness.txt` plus a `-r` reference. Repos with neither are skipped as non-Python. Validates the result with `tomllib` and restores the original rather than leaving a broken manifest. Called by `check-harness-deps.sh`; usable standalone as `declare-repo-deps.py <repo> <pkg-spec> [...]`. |
| `setup/reconcile-settings-templates.py` | **Owns the relationship between the two settings templates.** `templates/settings.json.template` ships to every installed project; `templates/settings.harness.json.template` generates the harness repo's own `.claude/settings.json`. They had silently diverged — as of 2026-08-30 the harness template was missing 14 hook registrations the project template carried, and held 4 it did not, so those 14 hooks fired in every installed repo and **not** in the repo where they are written and tested (including the whole tool-failure-memory loop). Enforces `hooks(harness) == hooks(project) + HARNESS_ONLY`, where `HARNESS_ONLY` is an explicit allowlist and each entry carries a written reason (currently one: `address-check-hook.sh`, which enforces a convention present only in the harness's own CLAUDE.md). `--check` reports drift and exits 1 — run by `/kiro:harness-validate`; `--sync` regenerates the harness template from the project one and is run by `install.sh` and `update.sh` *before* either copies a template anywhere. Idempotent. **Permissions are deliberately excluded**: the two files *should* differ there, since the harness grants itself write access to its own source tree that no target project may have, and denies `git push*` where projects only deny force-push. The workflow is add-to-project-template-then-`--sync`; editing the harness template directly is the drift the check catches. |
| `setup/gitnexus-reconcile.sh` | Keeps GitNexus's managed `CLAUDE.md` (or `AGENTS.md`, for projects that relocated their conventions there — `CLAUDE.md` wins on a tie) block honest about what is actually wired. `--wire` registers the `gitnexus` MCP server — writing it into `.mcp.json` and adding it to `enabledMcpjsonServers` in `.claude/settings.json` via `setup/gitnexus-mcp.py` (used by `install.sh --with-gitnexus`, replacing the old "paste this JSON yourself" note); `--check` exits 0 only when both the `.gitnexus/` index and the MCP server exist, gating whether `gitnexus setup` is allowed to write its MUST/NEVER block at all; with no flag it reconciles — stripping the block when it is dead, and when it is live repairing its skill paths plus rewriting any bare `gitnexus_*` tool names to the `mcp__gitnexus__*` form the MCP server actually exposes. Run by `install.sh` around `gitnexus setup` and by `update.sh` on every sync (non-fatal), because the block is committed while `.gitnexus/` is gitignored and the MCP server lives in local config, so a fresh clone otherwise inherits rules for tools it cannot call. No-ops for projects that never ran `gitnexus setup`. |

## Daily Maintenance & Evaluation

| Script | Purpose |
|---|---|
| `orchestration/daily-runner.sh` | Per-repo entry point for daily maintenance. Fires `/kiro:daily-maintenance` headlessly. Installed by `install.sh`; triggered nightly by Windows Task Scheduler (WSL) or `session-start-hook.sh` catch-up. |
| `orchestration/daily-orchestrator.sh` | Global orchestrator that iterates all registered projects and calls their `daily-runner.sh`. Before the per-repo loop it runs one harness-level task: a once-per-calendar-day fleet sync that executes `update.sh` so registered projects pick up harness changes without anyone typing anything (nothing else ever ran `update.sh` — `stop-hook.sh` only nudges). Gated by `.last-harness-sync` (day-string compare, no GNU-only `date -d`), guarded by `bash -n update.sh` so a half-written `update.sh` is never run fleet-wide, forwards `--repo`, prints `[would-sync]` under `--dry-run`, and opts out with `SDD_SKIP_HARNESS_SYNC=1`. Its inline drift-review gate does elapsed-days math with `python3`, not `date -d`, and the sweep writes to `$HARNESS_DIR/reports/drift-review-report.md` — the git-ignored `reports/` directory, not `docs/`, so a generated report never lands in tracked documentation. After the per-repo loop (full-fleet runs only, never `--dry-run`) it runs `utils/check-fleet-registration.sh --quiet` and logs any unregistered harness install to `logs/orchestrator.log` / `logs/orchestrator.stderr.log` — a report, never a gate. |
| `orchestration/setup-global-orchestrator.sh` | Register `daily-orchestrator.sh` with Windows Task Scheduler (schtasks). Ends with a **warn-only** preflight: runs `daily-orchestrator.sh --dry-run` through the same `wsl.exe -d <distro> -- bash -lc` path the task uses, and reports if it fails. Warn-only rather than fatal because the matching check (`schtasks /Run` + `LastTaskResult`) verifies Windows-side execution and could not be tested — verify by hand with the `/Query` line the script prints. |
| `orchestration/setup-linux-orchestrator.sh` | Register `daily-orchestrator.sh` with cron (Linux). Exits 1 unless a **preflight** passes: runs `--dry-run` under an approximated cron environment (`env -i`, `PATH=/usr/local/bin:/usr/bin:/bin`), since cron's near-empty environment is where a command that works interactively fails every night invisibly. The preflight also runs on the "already registered" path — that is exactly the state a silently-failing cron job reports. |
| `orchestration/setup-mac-orchestrator.sh` | Register `daily-orchestrator.sh` with launchd (macOS). Wraps the run in `caffeinate -i` so the LaunchAgent's unattended 18:00 fire isn't cut short by idle/display sleep. Exits 1 unless a **preflight** passes: registers a throwaway probe agent (`com.sdd.orchestrator-preflight`) that runs `--dry-run` in the same launchd context, waits up to 30s for its exit code, then boots it out. `launchctl load` returning 0 only proves registration, not that the job can execute — with the harness under `~/Documents` launchd exited 126 (`Operation not permitted`) daily for four days behind a green install. On failure the script names TCC explicitly when `$HARNESS_DIR` is under `~/Documents`, `~/Desktop` or `~/Downloads`, and gives both fixes (move the harness, or grant Full Disk Access to `/bin/bash`). Preflight also runs on the "already loaded" path. |
| `routines/macro-eval-runner.sh` | Runs `/kiro:macro-eval-sweep` headlessly for trend analysis. |
| `routines/harness-health-runner.sh` | Runs the bi-weekly harness health routine: CLAUDE.md review (Phase 1), iterative skill repair (Phase 2), and **token spend attribution (Phase 3)**. The runner executes `utils/token-forensics.py --days 14` itself and substitutes the output into `FORENSICS_PLACEHOLDER` in the prompt, rather than asking the headless session to shell out — a headless run that is merely *told* to run a script can skip it silently, and the phase would then report on nothing while looking like it ran. A missing script or non-zero exit is substituted as a visible marker, so the phase can report "no data" but can never invent figures. Substitution is `sed` for the date and `awk` with an env-var read for the report body, so the captured output's own characters are never interpreted as replacement syntax and a stray `TODAY_PLACEHOLDER` inside it cannot be expanded. Cadence `MIN_GAP_DAYS=13`; force with `HARNESS_HEALTH_FORCE=1`. |
| `routines/skill-curator-runner.sh` | Runs `/kiro:skill-extract` to curate and augment skills from session learnings. Before invoking the prompt, runs `utils/skill-dependency-scan.sh` and substitutes its output into `DEPENDENCY_MAP_PLACEHOLDER` so the sweep can flag cross-referenced skills before proposing delete/merge. |
| `routines/tool-failure-review-runner.sh` | Promotes recurring tool failures from `.claude/memory/tool-failures.jsonl` into `ERRORS.md` + memory. |
| `routines/security-report-runner.sh` | Daily security scan: runs the security-report prompt headlessly, writes report to `.claude/reports/security/`. Runs at most once per day (`SECURITY_REPORT_GAP_DAYS`). Opt out with `SDD_SKIP_SECURITY_REPORT=1`. |
| `routines/code-review-learning-runner.sh` | Self-improving code-review learning sweep: compares pr-babysit's logged reviews (`.claude/memory/pr-reviews/pr-<n>.md`) against real human review activity on merged PRs, promotes low-risk findings (conventions, dismissed-flag patterns) straight into memory, and reports higher-risk methodology changes to `docs/code-review-learning-report.md` for human approval. No-ops unless there's a merged+logged PR not yet processed; self-paces to weekly (`CODE_REVIEW_LEARNING_GAP_DAYS`, default 7) once there is. Applies to any repo. Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_CODE_REVIEW_LEARNING=1`. |
| `routines/startup-payload-audit.sh` | Deterministic (no LLM) daily audit of the fixed per-session startup token tax (`CLAUDE.md` + `@imports` + `.claude/rules/*` + auto-loaded `MEMORY.md`). Writes `.claude/reports/context/startup-payload.json`, read by the dashboard's Context Health tab. Self-paces to daily via its own state-file guard. Wired into `orchestration/daily-orchestrator.sh` `run_one()`. Opt out with `SDD_SKIP_STARTUP_AUDIT=1`. |
| `validate-behavior-spec.py` | Deterministic (no LLM) structural check for a `.claude/behaviors/<name>/BEHAVIOR.md` spec: file exists, frontmatter has `name`/`description`, `name` matches the parent directory. Called by `behavior-spec-agent` (`/kiro:daily-maintenance` Step 6b) after drafting or revising a spec; never run standalone. |

## Session Intelligence

> **No regex anywhere in this tree.** `ruff.toml` bans importing `re` (TID251). Every
> pattern match was replaced with an explicit parser on 2026-08-20 after `(\d+)%` read
> "24.5%" as 5 and the dashboard showed a wrong number for weeks without erroring. When
> a value has to be read back by a program, emit it as structured data at the source —
> `session/record_metric.py` is the reference for that.

| Script | Purpose |
|---|---|
| `detect_reexplanation.py` | Haiku-based session signal detector. Classifies sessions as drain (re-explanation) or charge (approval). Called by `hooks/claude/stop-hook.sh`. Runs Haiku through `claude --print` (subscription auth), **not** the `anthropic` SDK — the SDK needs a separately-billed `ANTHROPIC_API_KEY`, and with none set it failed silently on every session, which the dashboard rendered as "0 memory gaps". Sets `SDD_HEADLESS=1` on the child so the stop hook skips the detector and does not recurse. On failure it emits a `[detector-down]` observation and exits 4 — never a silent zero. |
| `record_metric.py` | Appends one measurement to `.claude/memory/metrics.jsonl` (`session-quality`, `keep-rate`, `memory-gap`). The dashboard reads this file and never re-extracts numbers from prose in `observations.md`. Same day + same metric replaces rather than appends. `--idle` marks routine windows with no user session so they are excluded from averages. Called by the `session-quality` and `keep-rate` skills and by `detect_reexplanation.py --record-metric`. |
| `micro_reflect.py` | Extracts durable facts from drain sessions → writes `[auto-learn]` entries to `hot-memory.md`. Can be invoked standalone on drain signals. |
| `trust_score.py` | Applies Judge score delta to the trust score line in `hot-memory.md`. |
| `session/write_handoff.py` | Deterministic (non-LLM) transcript-to-markdown session handoff. Reads the transcript path from stdin JSON, extracts branch/cwd/recent messages, writes `.claude/memory/handoff/latest.md`. Invoked with `--trigger precompact` from `compaction-discipline-hook.sh`, `--trigger agent-spawn` from `gbrain-agent-spawn.sh`, and `--trigger cache-cost` from `stop-hook.sh` when cache tokens hit ≥70% of session spend after ≥1 compaction; surfaced (if <24h fresh) by `session-start-hook.sh`. Never invoked manually. |

## PR Automation

| Script | Purpose |
|---|---|
| `pr/detect_base_and_create.sh` | Shared logic behind PR-babysitting automation. If a `gh-stack` is already active for the branch (`.git/gh-stack` exists — see the `stacking-pull-requests` skill), runs `gh stack submit --auto` for the whole stack instead and exits, skipping the single-PR path below. Otherwise: auto-detects a feature branch's true fork-point base (via `git merge-base` + most-recent-commit-date comparison across all local/remote refs, falling back to the repo's default branch) and idempotently opens a draft PR (`gh pr create --fill --draft`) if one isn't already open. Also checks for a `PULL_REQUEST_TEMPLATE.md` and backgrounds `pr/log_review.sh` via `nohup` once the PR exists. No-ops cleanly if `gh` isn't installed or the branch isn't inside a git work tree. Invoked from `hooks/claude/pr-auto-create-hook.sh` (after a successful non-force `git push`) and `hooks/claude/pr-mention-nudge.sh` (when the user's prompt mentions opening/creating a PR). Hands off to the `pr-babysit` skill (replaces the retired `iterate-pr` skill). |
| `pr/log_review.sh` | Headless `claude --print` invocation of the `gitnexus-pr-review` skill against an open PR. Writes `.claude/memory/pr-reviews/pr-<n>.md` (human-readable review) and `pr-<n>.review.json` (structured verdict/body/comments). Never posts to GitHub itself — backgrounded by `pr/detect_base_and_create.sh`, and re-runnable by the `pr-babysit` skill. |
| `pr/validate_review_json.py` | Schema validator for `pr-<n>.review.json` — checks `verdict` (APPROVE/REJECT), `body` (overview/concerns/issue_count/recommendation), and `comments[]` (path/line/side/start_line/start_side/body, with `body` required to start with `CRITICAL:`/`IMPORTANT:`/`SUGGESTION:`/`NIT:`). Run via `python3 .claude/scripts/pr/validate_review_json.py <path>` after `log_review.sh` writes the file, and by the `review-pull-requests.yml` GitHub Action's read-only "review" job before handing off to the write-permission "publish" job. |

## Utilities

| Script | Purpose |
|---|---|
| `skill-listing-budget.py` | Measures the **aggregate** cost of the skill listing — every installed skill's `name` + `description`, which is injected on every session unconditionally (bodies load only on invocation). Compares the total against a 1%-of-context-window ceiling for both 200k and 1M windows and lists the worst offenders. Exists because `skill-curator`'s per-skill thresholds (>150 ⚠️, >200 🔴) have no ceiling for the total, which made the aggregate decorative: every skill can pass individually while the sum is an order of magnitude over. First run on this machine: 995 skills, ~42.2k tokens — **21.1× over on a 200k window, 4.22× on 1M**. Also flags skills with no description at all (they consume a listing slot while giving the router nothing to match on, so they effectively never fire). `--strict` exits 1 when over budget; `--json` for machine consumption; `--dir` to scan a non-default skill root. Read the **ratio**, not the absolute — above ~2× the driver is skill count, not description length, so the fix is `skill-curator`'s deprecate/archive passes rather than compression. Invoked by `skill-curator` Phase 2. |
| `utils/token-forensics.py` | **Measures where tokens actually went**, from `~/.claude/projects/**/*.jsonl`. Every other token-related skill (`context-optimization`, `context-window-management`, `rtk-token-reduction`, `cost-optimization`) is prescriptive advice about reducing context; none measured actual spend, so none could say which advice would pay. Five analyses: deduplicated totals (same `requestId` collapse as the dashboard — naive summing overstates ~80%); **amplified per-tool cost** = chars returned × requests that followed it in the same session, which ranks what a tool *caused* rather than what it *returned* (a 20k-char read on turn 3 of a 200-turn session is millions of cache-read tokens; the same read on the last turn is nearly free); peak rolling 5h window, which is what a usage limit actually measures; session shape (peak concurrency, short-session count) as an automation fingerprint; and an automation split. That last one reports its own `method`: `isSidechain` would give an exact subagent split, but **measured 2026-08-30 it is present on every assistant line and `True` on none** — 0 of 6,423 across 150 transcripts in sessions that provably spawned agents — so each agent gets its own session file and the script falls back to a clearly-labelled short-session proxy, switching to the exact split automatically if the field ever starts being populated. It never prints an unpopulated field as `0%`, because unknown and zero are different findings. `--days`, `--project`, `--limit`, `--top`, `--json`. Read-only, no network. Driven by the `auditing-token-spend` skill and by Phase 3 of the bi-weekly harness-health routine. |
| `utils/dashboard-usage-dedup.test.sh` | Tests `dashboard.py`'s `_parse_session_file` token dedup (8 synthetic cases + a format-drift canary). One API response is written to the transcript as one JSONL line **per content block**, each repeating the identical `message.usage`; the pre-2026-08-30 parser summed line-by-line and inflated token totals ~83% on this machine's own logs, carrying the error into every USD figure. The canary reads real transcripts and **fails if it finds zero duplicates** — that would mean the transcript format changed and the dedup has silently become a no-op. SKIPs (does not fail) when `~/.claude/projects` is empty, so CI on a clean box still passes. |
| `dashboard.py` | Local harness dashboard (browser-based). Token totals are deduplicated on `requestId`/`message.id` before summing — see `utils/dashboard-usage-dedup.test.sh` for why, and `collapsed` in each session record for the drift canary. Includes Workshop tab for Raindrop traces. The GitNexus tab embeds the **hosted** web app (`GN_WEB_UI` = `https://gitnexus.vercel.app`, opened as `/?repo=<name>`, with `allow="local-network-access"` on the iframe) rather than iframing `gitnexus serve`, which ships no web UI — it is the API backend the hosted app calls at `http://localhost:4747`. The dashboard's own `/gn/` reverse proxy (`_proxy_gitnexus`, which rewrote asset URLs and injected a repo-auto-select script) is gone with it. Both the initial probe and the post-`serve`-start poll hit `GN_PROBE_URL` (`/api/repos`) in **real CORS mode**: `serve` 404s at `/`, and a `no-cors` fetch returns an opaque response, so a live-but-404ing server was indistinguishable from a dead one — a non-OK status now surfaces as `GitNexus API returned HTTP <code>` via the shared `gnOffline()` fallback. Maintenance Status section also shows a deferred-markers count via `count_debt_markers()`, which git-greps comment-anchored `DEBT:` markers across tracked non-md code (convention from the karpathy-guidelines skill). Skill Changes tab (companion mode) has "🔍 Analyze & Propose" / "✅ Apply Approved" buttons that drive skill-curator's propose/apply phases in a headless `claude --print` session, backing up `~/.claude/skills/` before any apply and logging to `logs/skill-curator-propose.log` / `logs/skill-curator-apply.log`. Context Health tab renders a live context-usage card (`_live_context_card()`) reading the per-repo state `hooks/global/caveman-statusline.sh` writes to `dashboard-context/<hash>.json`, keyed by `sha256(repo_path)`; ignored if older than 15 minutes (`LIVE_CONTEXT_MAX_AGE`). Session Quality tab reads `metrics.jsonl` via `parse_metrics()` — never prose — and shows three cards: avg session score (idle-routine days excluded), avg keep-rate, and memory gaps (a dash when the detector never ran, which is not the same as zero). The "AI adoption" card was removed on 2026-08-20: it divided Co-Authored-By-trailered commits by all commits, so in a single-developer repo it measured trailer hygiene rather than authorship, and its `(\d+)%` prose extraction read "24.5%" as 5%. Scheduled Tasks tab renders a scheduler that cannot run as a full-width red banner (`_scheduler_banner()`) **above** the routine cards, naming TCC explicitly on exit 126: the exit code was already parsed (un-shifting launchd's 32256 to 126) but shown as small yellow text beside a page of calm `PENDING` badges, and a dead scheduler invalidates everything under it. lean-ctx stats/ledger are read from `XDG_DATA_HOME/lean-ctx` (`~/.local/share/lean-ctx` by default, on macOS too — lean-ctx does not follow the "Application Support" convention `_platform_data_dir()` assumes; `~/.config/lean-ctx` holds only `config.toml`). |
| `check-no-hardcoded-paths.sh` | CI guard — fails if any harness source contains a machine-specific absolute path (`/home/`, `/Users/`, `/c/Users/`, `/mnt/c/Users/`, `C:\Users\`, or hardcoded `$HOME/.claude/sdd-harness`). Every path must be self-located via `lib/resolve-harness-dir.sh`. Scans `*.sh`, `*.py`, `*.json` and `*.template` — **config counts as code**: it originally scanned only `*.sh`/`*.py` and excluded `.claude/**` wholesale, so `.claude/settings.json` was invisible on both counts while holding 23 absolute hook paths, and the guard reported clean the entire time. Gitignored-but-generated files are re-admitted by name (`.claude/settings.json` only; `settings.local.json` is the user's and may legitimately hold absolute paths). Excludes `docs/**` (prose + frozen plan/spec records), `skills/**` (vendored third-party code and recorded benchmark output — 13 pre-existing violations drowned real findings), `lib/resolve-harness-dir.sh` and `lib/harness-pointer.sh` (the two allowed namers of these paths), and itself. Installed as the harness repo's `.git/hooks/pre-commit` by `install.sh` / `update.sh` — previously the hook existed in the source tree but nothing ever copied it, so it had never run automatically while both files advertised it as wired up. Also bans **tool-layout literals**, because a path can be `$HOME`-relative and still be a guess: `$HOME/.local/bin`, `$HOME/.local/share/uv`, `$HOME/.local/pipx`, `$HOME/.raindrop` and `$HOME/.cargo` are *defaults*, not facts (every one is relocatable by env var), and `/opt/homebrew` is Apple-Silicon-only — hardcoding it breaks every Intel Mac exactly as `/usr/local` breaks every Apple Silicon one. Use `lib/tool-paths.sh`, which is excluded from the scan as the one allowed namer. Lines whose literal is the fallback of a documented override (`${RAINDROP_HOME:-$HOME/.raindrop}`) are exempt — listed by variable name rather than by matching `${VAR:-` generally, so a real machine path smuggled in as some unrelated variable's default is still caught. |
| `utils/check-fleet-registration.sh` | Finds repos carrying a harness install (`.claude/scripts/orchestration/daily-runner.sh`) that are absent from `projects.txt`. Such a repo gets zero routines and appears nowhere — the dashboard only renders repos it is told about, so absence is not shown as failing, it is simply not shown. Scan roots are **derived** from `projects.txt` (the parent directory of each registered repo) rather than stored, keeping `projects.txt` the only file on disk that records a fleet path. Exit 0 when complete, 1 otherwise; `--quiet` suppresses the success line. Wired into `orchestration/daily-orchestrator.sh` (report-only) and `/kiro:harness-validate`. |
| `lib/harness-pointer.sh` | Sourced helper owning `$HOME/.sdd-harness-root` — **the** single stored pointer to the harness, and the only file on the machine that records where it lives. In-tree scripts self-locate via `lib/resolve-harness-dir.sh` and store nothing; cross-repo hooks run with cwd set to an installed *project*, so they cannot, and read this instead. A plain file rather than a symlink because Windows and Git Bash need elevated privileges to create symlinks; `~/.claude/sdd-harness` is kept as a convenience symlink **derived** from the pointer, refreshed alongside it and never read as an independent source. Exposes `write_harness_pointer` (install/update only), `read_harness_pointer` (returns 1 on missing *or* stale, so callers can tell "never installed" from "moved"), and `install_harness_pre_commit`, which drops `hooks/git/pre-commit` into the harness repo without clobbering a foreign pre-commit hook. |
| `lib/ship-safety-scan.sh` | Pre-ship gate run by `install.sh` / `update.sh` before any source is copied into a repo. Hard-blocks on leaked secrets / populated `.env` files (exit 1); soft-warns on over-broad permission rules in settings templates. Opt out with `SDD_SKIP_SHIP_SCAN=1`; promote warnings to failures with `SDD_SHIP_STRICT=1`. |
| `lib/project-gitignore.sh` | Sourced helper owning `SDD_GITIGNORE_ENTRIES` — the local-only set (`.claude/`, `specs/`, `CLAUDE.md`, `AGENTS.md`, `ERRORS.md`) appended to each project's `.gitignore` — plus the `ensure_gitignore <project_dir>` that applies it. Everything in the list is regenerable output rather than source: `.claude/` and `specs/` are rebuilt by `install.sh` / `update.sh`, `CLAUDE.md` is templated per project, `AGENTS.md` is written by `lean-ctx setup`, and `ERRORS.md` is a per-machine failure log. Sourced by **both** installers on purpose: `install.sh` runs once per project, so an entry added later would never reach an already-installed project, while `update.sh` calls it on every sync (git repos only — a non-repo has nothing to ignore and shouldn't grow a `.gitignore`) and backfills it. Idempotent: each entry is added only if an exact matching line is absent, the `# SDD harness — local-only, never committed` header is written at most once, and it always returns 0 because callers run under `set -e` and "nothing to add" is the normal case on every re-run. |
| `lib/project-gitignore.test.sh` | Tests the above (`bash scripts/lib/project-gitignore.test.sh`). Three cases: a pre-existing `.gitignore` keeps its content and gains each entry exactly once, with a second run leaving the file byte-identical and still exiting 0 — the case that matters, since `update.sh` runs under `set -e` and would abort every sync of an already-configured project on a non-zero "nothing to add"; a missing `.gitignore` is created with the header as its first line (no leading blank); and a legacy install holding only `.claude/`, `specs/`, `CLAUDE.md` gains `AGENTS.md` and `ERRORS.md` without duplicating what was already there. |
| `lib/tool-paths.sh` | **The one allowed namer of package-manager layouts.** Locates globally-installed CLIs by *asking* — `uv tool dir`, `uv tool dir --bin`, `pipx environment`, `brew --prefix` — then falling back to each tool's documented env var (`UV_TOOL_DIR`, `UV_TOOL_BIN_DIR`, `PIPX_HOME`, `RAINDROP_HOME`, `CARGO_HOME`) and only last to XDG spec defaults. Exposes `find_tool`, `find_tool_python`, `uv_tool_dir`, `uv_tool_bin_dir`, `pipx_*`, `brew_bin_dir`, `raindrop_bin_dir`, `cargo_bin_dir`, `tool_bin_dirs`, `ensure_tool_bin_on_path` (fixes PATH for the current process) and `persist_tool_bin_on_path` (fixes it for future shells via `uv tool update-shell`, returning 0=wired / 2=already there / 1=could not, so callers never announce work that did not happen). Exists because `command -v <tool>` is a PATH check, not a location check: `uv tool install` writes shims to a directory routinely absent from the PATH that `install.sh`/`update.sh` and Claude Code hooks run under, so an installed, running, healthy tool reads as absent and whole features skip themselves silently. Hardcoding the directory is not the fix — every one of these locations is relocatable by env var, so a baked-in path works on the machine it was written on and breaks on a clone. ~7ms per `uv tool dir` call, measured — cheap enough for a session-start hook. |
| `lib/tool-paths.test.sh` | Tests the above. The happy path proves little (a hardcoded default passes it too), so the real assertions are the relocation cases: with `uv` forced off PATH, `UV_TOOL_DIR`/`UV_TOOL_BIN_DIR`/`RAINDROP_HOME`/`CARGO_HOME` must all win, and `XDG_DATA_HOME`/`XDG_BIN_HOME` must be honoured as the last-resort fallback. Also asserts `brew_bin_dir` equals `brew --prefix`/bin rather than either hardcoded Homebrew location. |
| `lib/venv-tools.sh` | Sourced helper owning the harness's own Python venv at `<harness root>/.venv-tools` (gitignored). `venv_tools_python` resolves its interpreter across POSIX/Windows layouts; `venv_tools_ensure` creates or repairs it, preferring `uv venv --seed` and skipping uv-managed standalone interpreters whose `base_prefix` does not exist outside uv (a venv built from one dies with `ModuleNotFoundError: No module named 'encodings'`). Used by `setup/liteparse-setup.sh` and `setup/check-harness-deps.sh`; `hooks/claude/stop-hook.sh` no longer routes `session/detect_reexplanation.py` here — that script dropped its `anthropic` import and shells out to `claude --print` instead, so it runs on stdlib and the subscription. |
| `lib/repo-venv.sh` | Sourced helper for reaching into a **target repo's** Python environment. `repo_python` hunts `.venv`/`venv` under the repo root and `backend/`, `app/`, `src/` (never creating one — that layout is the repo owner's decision); `repo_has_env` distinguishes "no environment yet" from a real failure; `repo_has_module` probes importability; `repo_pip_install` installs and falls back to `uv pip install --python <venv>` when the venv was seeded without pip, printing the installer's actual output on failure. Replaces three near-identical inline copies in `raindrop-setup.sh`, `headroom-setup.sh` and `check-harness-deps.sh` that each ended in `-q 2>/dev/null`, making a failed install indistinguishable from a successful one. Carries a `timeout`/`gtimeout`/no-op shim because macOS ships neither. |
| `lib/env-detect.sh` | Sourced by `orchestration/daily-orchestrator.sh`. Detects host OS and WSL, and classifies a registered repo path as `cross-fs` when it's under `/mnt/*` on WSL — the one confirmed real perf risk (native-Windows-side dispatch was A/B-tested and does not fix it). Surfaces cross-fs repos as a `WARNING` line in `logs/orchestrator.log`; does not attempt to reroute or fix. |
| `headroom-setup.sh` | Installs `headroom-ai` globally + per registered-repo virtualenv, installs the persistent proxy service (launchd on macOS, systemd on Linux), and wires Claude Code to route through it durably (`headroom init --global --memory claude`) once the proxy's `/readyz` check passes. Removes any legacy `~/.bashrc`/`~/.zshrc` `alias claude='headroom wrap claude'` on re-run. **headroom is machine-level, not per-repo** — it works through `ANTHROPIC_BASE_URL` in the shell rc plus the proxy service, so no repo declares it and no repo dependency prune can touch it. The per-repo venv install was removed after measurement: it had succeeded in **zero** of four registered repos (hidden behind `-q 2>/dev/null`) while headroom worked fine throughout, because nothing imports headroom from a repo — `utils/sync-memories-to-headroom.py` runs under headroom's own interpreter. Add `headroom-ai` to `setup/repo-requirements.txt` if a repo ever needs `import headroom` in its own source. Resolves the binary through `~/.local/bin` and the uv-tool/pipx layouts rather than `command -v`, since `uv tool install`'s shim directory is off PATH in the environments `install.sh`/`update.sh` run under — the service and routing block was gated on a bare `command -v headroom` and was being skipped in total silence. The `/readyz` gate before wiring routing uses `--connect-timeout 3 -m 25` plus one retry: the endpoint answers instantly when warm but can exceed 8s while the compression model loads, and a false negative there silently leaves routing unwired. |
| `sync-memories-to-headroom.py` | Bidirectional sync: harness markdown memories ↔ headroom SQLite DB. Called at session start when headroom is installed. |
| `utils/skill-dependency-scan.sh` | Deterministic (grep, word-boundary) cross-reference scan: for every skill in `~/.claude/skills/*/`, finds referrers across other skills' SKILL.md bodies, hooks, agents, commands, CLAUDE.md, kiro rules, and routine scripts. Outputs `file:line` locations only, capped at 8 referrers per skill. Called by `routines/skill-curator-runner.sh` to build the dependency map injected into the skill-curator prompt; run standalone from the repo root for a one-off check. |
